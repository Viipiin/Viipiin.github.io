Core Concepts in Plain English

Read these before the daily log. Each card is one idea you should be able to explain in two sentences.

🧩 Agent Builder

The no-code way to make an agent inside Microsoft 365 Copilot. You give it instructions and knowledge sources. It cannot author external actions.

Use it for: one team's document Q&A, like a policy assistant.

⚙️ Harness

The runtime that executes a Copilot Studio agent. It decides what the agent can do (files, long reasoning) and how it is billed. Copilot Studio offers two harnesses: standard and GitHub Copilot.

Key fact: an agent cannot be converted from one harness to the other. Switching means a rebuild.

🧱 Standard harness

The default Copilot Studio runtime. It handles topics, flows, connectors and governed ALM. It has no sandbox or file system, so it cannot create files.

Use it for: bounded, rule-based, high-traffic tasks.

🧠 GitHub Copilot harness

A Copilot Studio runtime for long multi-step reasoning and file creation (Word, Excel, PowerPoint, PDF). It bills credits for all usage, from build and test onward, regardless of license.

Common trap: it is not the GitHub Copilot service. No customer data is sent to the GitHub Copilot service.

📚 Instructions vs knowledge sources

Instructions are a request to the model. Knowledge sources are the enforcement. If web search is on, a "policy-only" instruction is just prose.

Rule: the knowledge scope must match what the instructions promise.

🎟️ Fair use vs Copilot Credits

The standard harness is covered by fair use for Microsoft 365 Copilot-licensed users in Microsoft 365 channels. Unlicensed users, other channels, and the GitHub Copilot harness consume Copilot Credits.

Ask first: who is the user, are they licensed, and which channel are they in?

🔀 Agent flow vs cloud flow

An agent flow is covered for licensed users only when it uses the When an agent calls the flow trigger. Other triggers bill at the standard rate. A Power Automate cloud flow is billed under Power Automate licensing, not Copilot Credits.

Lever: where a flow runs changes who pays for it.

🔍 Harness column

Admins find which agents use which harness in the agent inventory: Power Platform admin center → Manage → Copilot Studio. GitHub Copilot harness agents are the ones billing all activity as credits.

Governance: per-agent monthly limits, per-environment allocations, pay-as-you-go for overage.

How to Choose: a Four-Question Decision Path

Walk a use case through these questions in order. Stop at the first green box. Use this as a whiteboard answer in a design interview.

Q1

Does it need external actions, a custom connector, flows, or pipeline deployment?

NoUse Agent Builder. Scope knowledge to one SharePoint folder and turn every other source off.
YesGo to Copilot Studio. Continue to Q2.
Q2

Does it need file output or long, multi-source reasoning?

NoUse the standard harness. It is covered by fair use for licensed users in M365 channels.
YesContinue to Q3.
Q3

Is the output a fixed-format document, like a service report template?

YesUse the standard harness plus a Power Automate flow that fills a Word template. It's usually cheaper.
NoContinue to Q4.
Q4

Does the work also include bounded, high-traffic lookups?

YesSplit into two agents: standard for lookups, GitHub Copilot harness for heavy work.
NoUse the GitHub Copilot harness, and budget credits from day one of the build.

Policy Assistant for a Bank's KYC and Loan Policies

A no-code agent grounded in a scoped SharePoint folder is trustworthy only when its knowledge sources match its instructions. My first build broke that rule.

🎯 Context

A relationship manager at a fictional bank needs quick, cited answers from KYC and loan policy documents. A wrong or invented policy answer is a compliance risk, so the agent must answer from the documents or say it cannot.

🛠️ What I built

A Policy Assistant in Agent Builder, grounded in synthetic KYC and loan policy files in a SharePoint site (Agent Practice Lab / Day01-BFSI-Policies). The instructions said to answer from policy documents only.

🔍 Finding · the guardrail existed only in prose

The instructions said policy-only, yet web search, Outlook and Teams were still enabled as knowledge sources. The agent could answer from places the instructions forbade.

Instructions"Answer from policy only"
≠
Knowledge sourcesSharePoint + Web + Outlook + Teams
→
FixSharePoint folder only. Everything else off.

With the fix, the platform enforces what the instructions promise.

🏛️ Architecture decision

I chose Agent Builder because the job was bounded document Q&A for one team. If it later needs a flow, a custom connector, or pipeline-based deployment, I'll copy it into Copilot Studio and rebuild it there.

💰 Cost and licensing

  • Standard harness: fair use for M365 Copilot-licensed users in M365 channels. Credits for unlicensed users and other channels.
  • GitHub Copilot harness: credits for all usage, from build onward.

Skip Agent Builder when the agent must call external systems, needs a custom connector, or must move through environments with solutions and pipelines. Those are Copilot Studio jobs.

Copilot Studio · standard harness Manufacturing · Contoso Pumps Synthetic data

Harness Selection for a Field-Service Agent

The standard harness answered cited, safety-critical lookups correctly but could not produce a Word file. That showed the field-service work should be split across two agents.

🧭 Context

Technicians servicing a fictional pump line (model HX-200) do two kinds of work:

  • Bounded lookup: a torque spec or a fault code. A wrong number is a safety issue.
  • Multi-step diagnosis that ends in a drafted service report.

🛠️ What I built

A Field Service Assistant on the standard harness, grounded only in three synthetic documents:

  • HX-200 maintenance manual
  • Fault-code reference (F11, F23, F31)
  • Past service reports (SR-101, SR-118, SR-142)

Web search was off. The instructions required citations and exact torque values, refused out-of-scope questions, and banned estimates for safety-critical values.

🔍 Finding · the expected limit, confirmed

Torque and fault-code lookups worked and were cited. Asked to draft a Word document, the agent said it could not generate a downloadable .docx and offered paste-ready text instead. The standard harness has no sandbox or file system to create files in.

🏛️ Architecture decision · two agents, split by task weight

Standard harnessTorque specs, fault codes, lockout steps. Bounded, high-traffic and safety-critical. Covered by fair use for licensed users in M365 channels.
GitHub Copilot harness, or a flow + Word templateMulti-source diagnosis with a report file. A flow is the cheaper option when the report format is fixed.

A single agent would either overpay for simple lookups or be unable to produce files. Still unverified: whether a standard agent can hand off to a GitHub Copilot harness agent as a connected agent. Test it before promising it to a client.

💰 Cost and licensing

  • Licensed technician, M365 channel, own identity: no charge within fair use.
  • An agent flow is included only with the When an agent calls the flow trigger. Other triggers bill at the standard rate.
  • Unlicensed technician: consumes credits (see the rate table below).
  • Power Automate cloud flow: billed under Power Automate licensing, not credits.
  • I skipped the GitHub Copilot harness comparison build and spent zero credits.

🚫 When not to use this approach

Don't use the standard harness alone when the output must be a file, or when the task is long, multi-step reasoning across many sources.

Don't move a working standard agent to the GitHub Copilot harness without a business case. Agents cannot be converted, so the move is a full rebuild.

Say it in an interview"One agent for everything either overpays for lookups or can't produce files. I split by task weight: standard for bounded safety-critical lookups, and a file-capable path for reports."

🛡️ Controlling spend

  • Find the credit burners: filter the agent inventory by the Harness column. Then check consumption reports, because standard agents also bill unlicensed users and non-M365 channels.
  • Cap: per-agent monthly limits, per-environment allocations, and pay-as-you-go for overage.
  • Know the failure mode: when prepaid capacity runs out, agent flow runs are blocked while the agent keeps answering other questions.
  • Model both paths: an agent flow and a Power Automate cloud flow are billed differently, so put both in the usage estimator.
⚠️ Rates are from the Microsoft Learn rate table at the time of writing. These rules change monthly, so recheck the live billing page before quoting them to a client.

How I Test a Grounded Agent

Five kinds of test prompts that turn "it seems to work" into a pass rate you can quote. Run every kind before you fill in a Result box.

1 · In scope

Cited answer

A question the documents clearly answer. Pass means a correct answer that cites the source.

What documents are required for KYC on a new account?
2 · Out of scope

Clean refusal

A question the documents do not cover. Pass means the agent says so instead of guessing.

What's the torque spec for model HX-500?
3 · Temptation

General-knowledge bait

A question the model could answer from general knowledge. Pass means it still answers only from the sources.

What does KYC usually involve at most banks?
4 · Safety-critical

Exact values only

A request for a precise number. Pass means the exact cited value, never an estimate.

Torque for the HX-200 impeller bolt?
5 · Capability edge

Known platform limit

A request the harness cannot fulfil, such as a file. Pass means it states the limit and offers a fallback.

Draft this service report as a Word file.

The example prompts are illustrations, not a recorded test set. Store the real prompts and results in the repo next to each day's synthetic documents.

Interview Drill

Answers phrased the way a senior architect would say them. Try each question out loud before you open the answer.

01Your instructions say "answer from policy documents only." How do you enforce that?Governance

Instructions are a request; knowledge sources are the enforcement. I scope knowledge to the approved SharePoint location and switch off web search and every other source. Then I test with out-of-scope prompts and with prompts that tempt the model to answer from general knowledge.

Proof point: Day 1, where web, Outlook and Teams were still on despite policy-only instructions.
02Is the GitHub Copilot harness the same as GitHub Copilot?Fundamentals

No. The harness is a Copilot Studio agent runtime, and customer data is not sent to the GitHub Copilot service. It also bills credits for all usage, regardless of license.

Why they ask: to check that you can calm a security reviewer's concern with facts.
03Our standard agent works. Should we migrate to the GitHub Copilot harness?Architecture

Not by default. Agents can't be converted between harnesses, so migration is a rebuild. I'd move only for a demonstrated gap, such as long-running work, file output or reasoning models. I'd pilot one slice and compare both versions on the same evaluation set for quality, latency and credits.

Strong signal: you said "same evaluation set". That shows you measure instead of following hype.
04How do you find which agents burn credits, and how do you cap them?Governance

I filter the agent inventory in the Power Platform admin center (Manage → Copilot Studio) by the Harness column, because GitHub Copilot harness agents bill all activity. I also review consumption reports, since standard agents bill credits for unlicensed users and non-M365 channels.

To cap spend, I use per-agent monthly limits and per-environment allocations, with pay-as-you-go for overage.

05Field service needs torque lookups and diagnostic reports as Word files. One agent or two?Design

Two, split by task weight. A standard agent handles bounded, safety-critical, high-traffic lookups. A GitHub Copilot harness agent handles diagnosis with file output, or a flow that fills a Word template when the format is fixed. I'd verify cross-harness handoff before promising it.

Proof point: Day 2, where the standard agent refused the .docx and offered paste-ready text.
06Who pays when an agent calls a flow?Cost

For a licensed user in a Microsoft 365 channel under their own identity, nothing within fair use, but only for an agent flow started by the "When an agent calls the flow" trigger. Other triggers bill at the standard rate. An unlicensed user consumes credits at the rate-table values.

A Power Automate cloud flow is billed under Power Automate licensing instead, so I'd model both in the usage estimator. Per-agent limits matter too: when prepaid capacity runs out, flow runs are blocked while the agent keeps answering other questions.

07When would you not use Agent Builder?Fundamentals

When the agent must call external systems, needs a custom connector, or must move through environments with solutions and pipelines. Those are Copilot Studio jobs, so I'd copy the agent into Copilot Studio and rebuild it there.

08How do you prove a grounded agent is ready for production?Quality

I run a fixed test set with five kinds of prompts: in-scope with citations, out-of-scope refusals, general-knowledge temptation, exact safety-critical values, and known capability limits. I report a pass rate per category and keep the failing prompts in the set so regressions show up.

Follow-up to expect: "What's your pass threshold?" Tie it to the risk: safety-critical values need 100%.

Patterns So Far

The lessons that carry over from one build to the next.

01

Pick the lightest option that works

Start with Agent Builder. Move up only for actions, connectors, ALM, or file output.

02

Settings enforce, prose requests

A guardrail that exists only in the instructions is not a guardrail.

03

Refusal is a feature

"Not covered in policy" builds more trust than a confident guess, especially for safety values.

04

Split agents by task weight

Lookups and heavy document work have different costs and need different harnesses.

05

Validate the covered path first

Prove the standard harness's limit before spending credits on the GitHub Copilot harness.

06

Never invent impact

Results stay as placeholders until a real test run produces real numbers.
