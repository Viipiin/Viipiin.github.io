The Agent Landscape at a Glance

The three harnesses I keep choosing between, and the signals that push a use case from one to the next.

Declarative

M365 Copilot Agent Builder

  • Internal, knowledge-only scenarios
  • Grounded over SharePoint folders
  • Fastest path from idea to working agent
Cost: covered by existing M365 Copilot licensing.
Standard harness

Copilot Studio

  • External actions and deterministic flows
  • Scoped knowledge with hard guardrails (e.g. web search off)

Cost: largely covered for licensed users in M365 channels.
Agentic harness

GitHub Copilot Harness

  • Long-running, multi-tool work
  • File-heavy tasks and document output
  • Multi-source diagnostics

M365 Copilot Agent Builder Declarative agent BFSI

Mapping Microsoft's Agent Landscape, and a BFSI Policy Assistant

🎯 Business problem

Branch staff need fast, consistent answers on KYC and loan-document rules without searching policy files.

🛠️ Solution

A policy-grounded agent over a SharePoint knowledge folder. The instructions require citations, and the agent answers "not covered in policy" instead of guessing.

🔁 How it works

Branch staffAsks a KYC / loan-doc question
→
Declarative agentInstructions: cite or refuse
→
SharePoint folderApproved policy documents only
→
AnswerCited response, or "not covered in policy"

🏛️ Architecture decision

Chose Agent Builder because the need is internal, knowledge-only, and covered by licensing. I also documented when to move up: to the Copilot Studio standard harness for external actions or a deterministic flow, or to the GitHub Copilot harness for long-running, multi-tool, file-heavy work, along with the licensing cost impact of each.

Copilot Studio Standard harness Manufacturing

Harness Selection for a Manufacturing Field-Service Agent

🧭 Context

A field-service scenario with two task types: bounded manual lookups, and long, multi-source diagnostics that end in a document.

🛠️ Built

A standard-harness Copilot Studio agent grounded only in a scoped SharePoint knowledge source, with web search disabled as a hard guardrail. It returned cited torque values and declined out-of-scope models.

🔍 Finding

Asked for a Word document, the agent said it couldn't generate a .docx and offered paste-ready text instead. That's the expected limit of the standard harness: it has no sandbox for file creation.

🏛️ Architecture decision · two-agent split by task weight

Standard harnessHigh-volume, safety-critical lookups: torque specs, manual references, scoped and cited.
GitHub Copilot harness, or a flow + Word templateDocument-heavy, multi-source diagnostics that need file output.

💰 Cost reasoning

The standard harness is largely covered for licensed users in M365 channels. The GitHub harness bills credits from build time onward. I validated the standard path at zero credit cost by deferring the GitHub harness build.

Patterns So Far

What carries over from one build to the next.

01

Pick the lightest harness that works

Start declarative. Move up only when you need actions, deterministic flows, or file output.

02

Refusal is a feature

"Not covered in policy" and declining out-of-scope models build more trust than a confident guess.

03

Scope the grounding hard

One SharePoint source, web search off. In safety-critical domains, a narrow source is the guardrail.

04

Split agents by task weight

High-volume lookups and heavy document work have different costs and different harnesses. Don't force one agent to do both.

05

Defer credit-billed builds

Validate the covered path first. Only start the GitHub harness once the standard path has proven its limit.

06

Never invent impact

Impact fields stay as placeholders until a real test run produces real numbers.
