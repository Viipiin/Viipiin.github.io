What is the difference between Xrm.Page and formContext? Which should you use today?

Theory
▼

Xrm.Page is deprecated since D365 v9. formContext is the modern approach — derived via executionContext.getFormContext(). It is scoped to the specific form instance, making it reliable in multi-form and UCI scenarios.

Always accept executionContext as your first parameter and derive formContext from it. Never use Xrm.Page in new development.
function onLoad(executionContext) {
    var formContext = executionContext.getFormContext();
    // use formContext safely
}

Write a plugin that auto-sets a "Welcome Note" on a new Contact record.

Practical
▼ 
using Microsoft.Xrm.Sdk;
using System;

public class ContactCreatePlugin : IPlugin
{
    public void Execute(IServiceProvider serviceProvider)
    {
        var context = (IPluginExecutionContext)
            serviceProvider.GetService(typeof(IPluginExecutionContext));

        if (context.MessageName != "Create" || context.Stage != 20) return;
        if (context.PrimaryEntityName != "contact") return;

        var target = (Entity)context.InputParameters["Target"];
        target["description"] = $"Welcome! Record created on {DateTime.UtcNow:yyyy-MM-dd}.";
    }
}
Register at Stage 20 (Pre-Operation) so the value is part of the original Create — no extra Update needed, saving a DB round-trip.

What are Pre-Images and Post-Images? Why are they necessary?

Theory
▼

On an Update message, Target only contains changed fields. To read unchanged field values, you need a Pre-Image.

Entity preImage = context.PreEntityImages["ContactPreImage"];
string oldEmail = preImage.GetAttributeValue<string>("emailaddress1");

Entity target = (Entity)context.InputParameters["Target"];
// Use pre-image value if field wasn't changed in this update
string currentEmail = target.Contains("emailaddress1")
    ? target.GetAttributeValue<string>("emailaddress1")
    : oldEmail;
Register the Pre-Image in Plugin Registration Tool, specifying the alias (e.g., "ContactPreImage") and the specific fields you need. Do not request all fields — impacts performance.

How do you prevent an infinite plugin loop?

PracticalCommon Interview
▼

Three strategies:

1. Check Depth — if a plugin updates the same entity, D365 re-fires it. Guard against this:

if (context.Depth > 1) return;

2. Filtering Attributes — register the step to fire only when specific fields change. If your plugin doesn't write those fields, it won't re-fire.

3. Flag Field — set a boolean new_isprocessed = true and skip execution if already set.

What are the key steps to register a plugin using Plugin Registration Tool?

Practical
▼
  1. Connect PRT to your D365 environment
  2. Register Assembly — upload .dll, choose Isolation Mode = Sandbox
  3. Register Step:
    • Message: Create / Update / Delete
    • Primary Entity: account / contact / etc.
    • Stage: Pre-Validation (10), Pre-Op (20), or Post-Op (40)
    • Mode: Synchronous or Asynchronous
    • Filtering Attributes: specific fields only (best practice)
  4. Register Images if needed — Pre/Post with alias and field list
  5. Test in D365 and verify Plugin Trace Log
Always specify Filtering Attributes on Update steps — otherwise the plugin fires on every single field change, degrading performance.

What is a Business Process Flow (BPF) and when do you use it?

Theory
▼

A BPF is a guided UI process overlay that walks users through predefined stages and steps. Each stage can enforce required data before progressing.

Example — Sales process: Qualify → Develop → Propose → Close

Each stage has steps (required fields). Users cannot move to the next stage until steps are complete. BPF stores progress in its own Process entity table, enabling stage-level reporting.

What is a Business Rule and when do you prefer it over JavaScript?

Theory
▼

Business Rules are no-code if-then logic on a form/entity that can set field values, show/hide fields, set required levels, show error messages, and lock/unlock fields.

Prefer Business Rules when: simple if-then logic, maintainable by admins without developer, or when server-side enforcement is needed (Entity scope).

Use JavaScript when: Web API calls, complex multi-condition loops, cross-form interactions, or advanced Xrm API features are needed.

What is the difference between row context and filter context in DAX?

Theory
▼
ContextWhen CreatedScope
Row contextCalculated columns, iterator functions (SUMX, FILTER)Evaluates expression for each row of a table
Filter contextReport visuals, slicers, page/report filters, CALCULATELimits which rows are visible across the model
Row context does NOT automatically filter related tables — you need RELATED() or CALCULATE() to transition a row context into a filter context.

Example: In a calculated column Sales[Margin] = Sales[Revenue] - Sales[Cost], DAX iterates each row — that is row context. When a visual shows total margin for "North" region, the slicer creates a filter context restricting rows to North.

2

How does CALCULATE work and what makes it so powerful?

TheoryPractical
▼

CALCULATE(expression, filter1, filter2, ...) does two things:

  1. Copies the current filter context
  2. Applies the filter arguments (add, modify, or remove filters) — then evaluates the expression in the new context
-- Total sales only for "Bike" category, regardless of any slicer
Bikes Sales = CALCULATE([Total Sales], Products[Category] = "Bikes")

-- Previous year total (uses ALL to remove date filters, applies a new date range)
PY Sales = CALCULATE([Total Sales], SAMEPERIODLASTYEAR(Dates[Date]))

-- Remove all filters from a column
All Customers Sales = CALCULATE([Total Sales], ALL(Customers))
CALCULATE is the only DAX function that can transition row context into filter context — critical for measures inside iterators.

What is the difference between SUM and SUMX? When would you use SUMX?

TheoryPractical
▼
FunctionBehaviourUse When
SUM(column)Aggregates an existing numeric column directly — single pass, fasterColumn already contains the value to sum
SUMX(table, expression)Iterates each row of table, evaluates expression per row, then sums resultsYou need to compute a value per row first (e.g. Qty × Price)
-- SUM: column already stores revenue
Total Revenue = SUM(Sales[Revenue])

-- SUMX: margin must be calculated per row first

-- More complex: apply discount per row
Discounted Revenue = SUMX(Sales, Sales[Revenue] * (1 - Sales[Discount]))
Overusing SUMX on large tables can hurt performance. Prefer SUM on pre-calculated columns where possible.

Explain FILTER, ALL, and ALLEXCEPT — how do they differ?

▼

What are DAX variables (VAR/RETURN) and why should you use them?

Practical
▼

Variables store intermediate results inside a DAX expression. They are evaluated once at the point of definition, not repeatedly. This gives two benefits: performance (avoids re-evaluation) and readability.

-- Without VAR: [Total Revenue] evaluated twice
YoY % = DIVIDE(
  [Total Revenue] - CALCULATE([Total Revenue], SAMEPERIODLASTYEAR(Dates[Date])),
  CALCULATE([Total Revenue], SAMEPERIODLASTYEAR(Dates[Date]))
)

-- With VAR: cleaner and [PY] evaluated only once
YoY % =
VAR CurrentRev = [Total Revenue]
VAR PYRev     = CALCULATE([Total Revenue], SAMEPERIODLASTYEAR(Dates[Date]))
VAR Change    = CurrentRev - PYRev
RETURN
  DIVIDE(Change, PYRev, BLANK())
VAR also captures the filter context at the point it is defined — useful for comparing context inside vs outside an iterator.

What is the difference between RELATED and RELATEDTABLE?

TheoryPractical
▼
FunctionDirectionReturns
RELATED(column)Many-side → One-side (follow relationship upward)Single value from the related dimension
RELATEDTABLE(table)One-side → Many-side (follow relationship downward)A filtered table of related rows from the fact table
-- RELATED: in Sales table calculated column, bring in the Category from Products

8

Why should you use DIVIDE instead of the / operator in DAX?

Practical
▼

The / operator returns an error when the denominator is zero or BLANK, which causes visuals to break or show errors. DIVIDE handles this gracefully with an optional alternate result.

-- Risky: will error or show infinity when denominator = 0
Profit Margin = [Profit] / [Revenue]

-- Safe: returns BLANK() when Revenue = 0 (BLANK is ignored by visuals)
Profit Margin = DIVIDE([Profit], [Revenue])

-- Or return 0 instead of BLANK
Profit Margin = DIVIDE([Profit], [Revenue], 0)
Use BLANK() (default) as alternate result — it means the visual treats missing data correctly. Use 0 only when you specifically want to display zero for missing data.

What is incremental refresh in Power BI and when should you use it?

TheoryPractical
▼

Incremental refresh divides a dataset into archive partitions (historical data, never refreshed) and rolling partitions (recent data, refreshed on schedule). Only recent partitions are refreshed each time.

Requirements:

Power Query / M Language

Query folding, Merge vs Append, custom functions, error handling

1

What is query folding and why does it matter?

Theory
▼

Query folding means Power Query translates your M transformation steps into a native query (SQL, OData) and sends it to the data source. The source does the heavy lifting — only results come back to Power BI.

Without folding, Power Query downloads all raw data and transforms it locally — far slower for large sources.

How to verify: Right-click any step in Applied Steps → if "View Native Query" is available (not greyed out), that step folds.

Common steps that break folding:

  • Adding a custom column with a non-foldable expression
  • Using List functions or Text functions not supported by the source
  • Merging with a local table
Once folding breaks at a step, all subsequent steps also lose folding. Put filtering steps (date ranges, column selection) as early as possible before any non-foldable steps.

How does RLS work with Composite models where some tables are DirectQuery?

Theory

Performance & Optimization

1

How does VertiPaq (in-memory columnar storage) work and what affects compression?

Theory
▼

Power BI Import mode stores data in VertiPaq — a columnar, in-memory compressed store. Key compression principles:

  • Dictionary encoding: Each unique value in a column gets an integer ID — repeated values store as tiny integers, not full strings
  • Run-length encoding: Long sequences of the same value are stored as (value, count) pairs
  • Cardinality is the enemy of compression: A column with 1M unique values (e.g., GUID, timestamp) compresses poorly and consumes enormous memory

Practical implications:

  • Remove GUID columns you don't need in DAX
  • Split DateTime into separate Date and Time columns — Date compresses well; time has 86,400 possible values per day
  • Remove free-text columns (notes, comments) — near-zero compression
Use VertiPaq Analyzer (free, in DAX Studio) to see exactly which columns use the most memory and have the highest cardinality. Focus optimization on the top 5 offenders.

  • Include common misspellings or alternative terms your users actually use
  • Avoid overlap between topics — if two topics have similar phrases, the NLU may trigger the wrong one
  • Use the Topic Overlap Checker (Topics page → Analyze) to detect conflicts
Very short trigger phrases (1–2 words) cause false positives. Prefer full sentences. Never use the same phrase in two topics — the last topic alphabetically wins, which is unpredictable.
7

How do you customize the Fallback topic to handle unrecognized inputs gracefully?

Practical
▼

A robust Fallback topic pattern:

  1. Increment a counter variable Global.FallbackCount at the start
  2. If FallbackCount = 1: rephrase request — "I didn't quite get that. Could you try asking in a different way?"
  3. If FallbackCount = 2: offer menu of topics — "Here are some things I can help with:" + quick reply buttons
  4. If FallbackCount >= 3: escalate to human — Redirect to Escalate topic; reset counter
If you have Generative Answers enabled, add a Generative Answers node before the retry counter check. The AI may resolve the query from knowledge sources without hitting the manual fallback path at all.

What is slot filling and how does Copilot Studio handle it automatically?

TheoryPractical
▼

Slot filling is the automatic extraction of entity values from a user's message — even when those values are provided before the bot explicitly asks for them.

Example: Your topic has two Question nodes — "What date?" (Date entity) and "What type of leave?" (Choice entity).

Slot filling works best when entities have clear, distinct patterns. Avoid overlapping entity patterns across Question nodes in the same topic — the bot may fill the wrong slot.

Power Automate Integration

Calling flows, passing variables, adaptive cards, error handling, limits

1

How do you call a Power Automate flow from a Copilot Studio topic?

Practical
▼
  1. In the topic, click + → Call an action → Create a flow or select an existing flow
  2. The flow must use the "When Copilot Studio calls a flow" trigger (Power Virtual Agents connector)
  3. The flow must end with a "Return value(s) to Copilot Studio" action (also PVA connector)
  4. Input parameters defined in the trigger become available in the topic's Action node as input fields
  5. Output parameters defined in the Return action become topic variables after the action executes
The flow must be in the same Power Platform environment as the Copilot Studio agent. Cross-environment flow calls are not supported natively.
2

How do you pass variables to a flow and get results back into the topic?

Practical
▼

Passing to flow (inputs): In the Power Automate flow trigger, add input parameters (Text, Number, Boolean, etc.). In the Copilot Studio Action node, map topic/global variables to those inputs.

Returning from flow (outputs): In the flow's "Return value(s) to Copilot Studio" action, add output parameters. Back in the topic, the Action node offers each output as a new variable to store the result.

// Flow trigger inputs:
//   EmployeeEmail (Text), LeaveType (Text), StartDate (Text), Days (Number)

// Flow return outputs:
//   RequestId (Text), ApprovalStatus (Text), ManagerEmail (Text)

// In topic after action runs:
// Topic.RequestId = "REQ-20450"
// Topic.ApprovalStatus = "Pending"
Keep flow inputs as simple types (Text, Number) — avoid passing complex JSON objects as strings. If you need to pass a record, serialize it with JSON() in Power Fx and deserialize with ParseJSON() in Power Automate.
3

How do you send an Adaptive Card and capture the user's response from a Teams flow?

Practical
▼

Use the Teams "Post an Adaptive Card and wait for a response" action in Power Automate:

  1. In the flow, add action: Microsoft Teams → Post an Adaptive Card and wait for a response
  2. Set Recipient to @{triggerBody()?['text']} or a specific email
  3. Paste the Adaptive Card JSON (design at adaptivecards.io)
  4. The action waits (up to 30 days) for the user to submit the card
  5. Capture body('Post_Adaptive_Card')['data'] to read submitted values
  6. Return the submitted values to Copilot Studio via Return action
For real-time bot conversations, the "wait for response" Teams action pauses your flow. Ensure the flow timeout setting allows sufficient wait time. For Copilot Studio, the synchronous 2-minute limit applies — for approvals, send the card asynchronously and have the approval update a Dataverse record the bot polls.
4

How do you handle failures when a called Power Automate flow fails?

Practical
▼

Flow failures don't automatically surface a descriptive error in Copilot Studio. Use an explicit error status pattern:

  1. In the flow's Return action, add an output parameter: Status (Text) — set to "Success" normally
  2. Add a Configure run after scope on error → return Status = "Error" and ErrorMessage = "..."
  3. In the Copilot Studio topic after the Action node, add a Condition: Topic.Status is "Error"
  4. On error branch: show a friendly message and optionally redirect to Escalate topic
Always design flows to return a status code. Never let a flow silently fail — users will see the bot hang or give a generic error message that erodes trust.
5

What is the execution timeout for flows called from Copilot Studio? How do you handle long-running operations?

Theory
▼

Flows called from Copilot Studio must complete within 2 minutes (120 seconds). If the flow exceeds this, the bot receives a timeout error.

Pattern for long-running operations:

  1. Trigger async: The bot calls a "submit" flow that kicks off the long operation and immediately returns a job/request ID
  2. Store ID: Bot stores the request ID in a global variable
  3. Status check: Bot asks "Would you like me to check the status?" — calls a lightweight "check status" flow with the job ID
  4. Notification (preferred): Long-running flow sends a Teams message when complete, or updates a Dataverse record that the bot checks on next user interaction

How does content safety and moderation work in Copilot Studio?

Theory
▼

Copilot Studio uses Azure AI Content Safety filters for both input and output moderation:

  • Harm categories: Violence, hate speech, sexual content, self-harm — filtered at configurable thresholds
  • Grounded responses only: When knowledge sources are configured, the AI is instructed not to answer from outside those sources
  • Custom blocked topics: You can explicitly add topics the bot should refuse (e.g., competitor comparisons, political discussions)
  • Sensitive topic handling: Built-in policies for firearms, financial advice, medical advice — bot deflects to appropriate resources

Governance: Content safety settings are at the agent level. DLP policies in the Power Platform admin centre control which connectors can be used, and tenant-level AI usage policies can restrict generative AI features entirely.

Never assume content filters are 100% effective. For bots handling sensitive use cases (mental health, legal, medical), always include a human escalation path and review AI responses during UAT with adversarial test inputs.

Users say the bot triggers the wrong topic for their questions. How do you diagnose and fix this?

Scenario
▼

  2. Check topic overlap: Topics page → Analyze → Topic Overlap checker highlights competing triggers.

  5. Review conversation transcripts in Analytics for the real user phrases — users often phrase things differently than authors expect.
